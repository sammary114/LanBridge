# LanBridge 协议实验方案与抓包计划

本文档规划后续分阶段实验方案。所有主动实验均在**自有受控环境**（宿主机与 Windows Sandbox 或专用虚拟机）中执行，严禁向局域网广播未经验证的攻击性报文或向真实用户发送伪造消息。

1. **同版本安装包已就绪**：
   * 宿主机下载目录已确认存在：`C:\Users\sammary\Downloads\nwt_setup_3.4.3055.exe`（43,437,496 字节）
   * 可通过挂载目录或直接拖拽方式在 Windows Sandbox 中运行安装。
2. **隔离网络端点**：
   * 宿主机虚拟接口：`172.31.112.1/20`
   * Windows Sandbox 实例：`172.31.122.254/20`（或 Sandbox 每次重启分配的虚拟 IP）
3. **抓包过滤准备**：
   ```text
   udp.port == 9011 || udp.port == 9012 || udp.port == 2425 ||
   tcp.port == 9011 || tcp.port == 9012 || tcp.port == 2425
   ```

## 分阶段实验矩阵

### 实验 1：宿主机单机静置基线抓包 (`01-host-idle.pcapng`)

* **实验目的**：获取单个内网通客户端处于空闲运行状态时的网络行为基线（心跳间隔、周期性广播与外网请求）。
* **待验证假设**：
  * **H1.1**：在没有对端响应时，宿主机每隔固定周期（例如 10s 或 30s）会向 `9011` 发送发现广播。
  * **H1.2**：空闲状态下不存在与外部未知 IP 的大量数据通信。
* **操作步骤**：
  1. 关闭 Windows Sandbox。
  2. 宿主机确保 `ShiYeLine.exe` 正在运行。
  3. Wireshark 启动捕获 `vEthernet (Default Switch)` 与物理网卡。
  4. 完全静置 30 秒，不进行任何 UI 操作。
  5. 停止抓包并保存为 `captures/01-host-idle.pcapng`。

### 实验 2：主动上线通告与网段探测抓包 (`02-discovery-trigger.pcapng`)

* **背景说明**：经核实，内网通 3.4.3055 的联系人列表界面并没有单独的“刷新联系人”按钮，其用户发现主要依赖以下机制：
  1. **状态切换广播**：客户端由“离线/离开”切换为“我在线上”时触发的全网通告。
  2. **网段扫描 / 一键添加**：主界面底部的“一键添加”图标（放大镜 `IDS_ONE_KEY_ADD_CONTACTOR`）主动扫描局域网。
  3. **定时自动刷新**：设置中开启的“自动刷新”（`IDS_AUTO_REFRESH`）周期机制。
* **实验目的**：捕获客户端主动触发上线广播或网段探测时产生的数据包。
* **待验证假设**：
  * **H2.1**：状态切换为“我在线上”时，客户端在 `UDP 9011` 或 `UDP 2425` 发送广播通告帧。
  * **H2.2**：点击“一键添加”扫描内网时，客户端向局域网广播或常见网段（如 `172.31.x.x`）逐 IP 发送探测包。
  * **H2.3**：广播或探测报文中包含客户端自身的用户 ID、组织号或主机名。
* **操作步骤（二选一）**：
  * **方式 A（状态切换通告，推荐）**：
    1. 启动 Wireshark 捕获。
    2. 在宿主机客户端左上角头像旁，点击状态下拉菜单，将“我在线上”切换为“离开”或“忙碌”，静置 3 秒，再切回“我在线上”。
    3. 记录切换时间。
    4. 抓包 10 秒后停止，保存为 `captures/02-discovery-trigger.pcapng`。
  * **方式 B（一键添加/局域网扫描）**：
    1. 启动 Wireshark 捕获。
    2. 点击主界面底部“一键添加”（放大镜图标），触发“正在自动扫描您所在的局域网...”。
    3. 观察 Wireshark 中是否有大量探测流量，几秒后取消扫描。
    4. 保存为 `captures/02-discovery-trigger.pcapng`。

### 实验 3：Sandbox 实例启动与双端发现抓包 (`03-sandbox-discovery.pcapng`)

* **实验目的**：观察两个客户端初次相遇、相互握手与建立点对点映射的全过程。
* **待验证假设**：
  * **H3.1**：新端点启动时首先在 `9011` 广播自身信息。
  * **H3.2**：对端收到后通过 `9012` 单播响应或发起握手。
  * **H3.3**：双端在 `9012` 上交互的 28 字节载荷（Opcode 0x86）是在此阶段交换生成的。
* **操作步骤**：
  1. 宿主机 Wireshark 在 `vEthernet (Default Switch)` 上开始捕获。
  2. 启动 Windows Sandbox，运行 `nwt_setup_3.4.3055.exe` 完成安装并启动客户端。
  3. 观察宿主机与 Sandbox 的联系人列表中是否出现对端图标。
  4. 待双方均显示“在线”后停止抓包，保存为 `captures/03-sandbox-discovery.pcapng`。

### 实验 4：普通文本消息收发抓包 (`04-text-message.pcapng`)

* **实验目的**：确认两台自有客户端之间收发单条普通纯文本消息所使用的端口、传输协议和加密情况。
* **待验证假设**：
  * **H4.1**：文本消息采用 `UDP 9012` 发送，还是建立 `TCP 9012` / `TCP 2440` 连接发送？
  * **H4.2**：消息内容是否为明文（GBK/UTF-8）或经过私有加密/压缩？
  * **H4.3**：每条消息是否遵循类似的 Request-ACK 确认机制？
* **操作步骤**：
  1. 双端保持在线。
  2. 启动 Wireshark 捕获。
  3. 宿主机向 Sandbox 发送一条特定测试文本（例如 `LANBRIDGE_TEST_MSG_001`）。
  4. 记录发送时间与接收时间。
  5. Sandbox 收到消息并显示在聊天窗口后，Sandbox 回复 `LANBRIDGE_REPLY_002`。
  6. 停止抓包，保存为 `captures/04-text-message.pcapng`。

### 实验 5：组织号影响对照实验 (`05-org-id-contrast.pcapng`) [可选]

* **实验目的**：验证设置中的“组织号”如何影响本地数据包字段（特别是 `corp id` 与 28 字节二进制载荷）。
* **待验证假设**：
  * **H5.1**：设置不同组织号后，双方无法互相发现，或在 9011/9012 交互时被拒。
  * **H5.2**：`POST /api/report.php` 中的 `corp id` 发生改变，且与填写的组织号存在特定哈希关系。
* **操作步骤**：
  1. 将 Sandbox 中的组织号修改为自定义字符串（如 `TESTORG123`）。
  2. 抓取刷新联系人与点对点报文。
  3. 保存为 `captures/05-org-id-contrast.pcapng`。

### 实验 6：窗口抖动实机交互验证 (`06-flash-screen.pcapng`) [TODO: 用户配合抓包]

* **实验目的**：获取两台官方内网通客户端之间双向发送“窗口抖动 / 闪屏”的真实 UDP 9012 ENet 报文序列。
* **待验证假设**：
  * **H6.1**：窗口抖动发送 Opcode `0x03EF`（十进制 1007），载荷为 `<X_SEND_FLASH_SCREEN docver="1"><TYPE>0</TYPE></X_SEND_FLASH_SCREEN>`。
  * **H6.2**：使用标准 ENet `SendReliable`（0x86）发送，对端立即回送 ENet ACK（0x01）。
  * **H6.3**：客户端本地存在 10 秒防连点抖动频控机制。
* **用户配合操作步骤**：
  1. 宿主机与 Sandbox 内网通保持好友在线并打开聊天窗口。
  2. 宿主机启动 Wireshark 捕获 `vEthernet (Default Switch)` 网卡。
  3. 宿主机点击聊天窗口工具栏的“发送窗口抖动”图标（晃动窗口图标）。
  4. 观察 Sandbox 窗口震荡与音效；间隔 5 秒后，在 Sandbox 窗口反向向宿主机点击一次“发送窗口抖动”。
  5. 停止抓包，保存为 `captures/06-flash-screen.pcapng`。

### 实验 7：文件传输全流程实机抓包 (`07-file-transfer.pcapng`) [TODO: 用户配合抓包]

* **实验目的**：捕获在线文件发送邀请、接收方接受、TCP 2440 高速数据流直传、UDP 进度同步与完成校验全过程。
* **待验证假设**：
  * **H7.1**：发送方在 UDP 9012 上发送 `<X_SEND_FILE>`，携带 `TASK_ID`、文件名、大小、时间戳和校验令牌 `PWD`。
  * **H7.2**：接收方点击“接受”后，通过 UDP 9012 回复 Opcode `0x03F3`（`<X_OPERATE_RECV_FILE>`，`OP=1`），并主动建立连接至发送方 TCP 2440 端口。
  * **H7.3**：传输期间接收方通过 Opcode `0x03F4`（`<X_PROGRESS_RECV_FILE>`）周期性向发送方通报实时进度与传输速率。
* **用户配合操作步骤**：
  1. 准备一个轻量测试文件（例如 5MB~10MB 的 `test_sample.zip`）。
  2. 宿主机启动 Wireshark 捕获。
  3. 宿主机向 Sandbox 拖入或选择该文件发起发送。
  4. Sandbox 聊天窗口出现文件卡片，点击“接受”（或另存为到桌面）。
  5. 等待进度条走完、提示“接收成功”。
  6. 停止抓包，保存为 `captures/07-file-transfer.pcapng`。

### 实验 8：消息与文件撤回实机抓包 (`08-message-recall.pcapng`) [TODO: 用户配合抓包]

* **实验目的**：验证消息和文件撤回时的网络信令格式与对端响应行为。
* **待验证假设**：
  * **H8.1**：撤回信令复用 Opcode `0x03EC` 传输，JSON 载荷内 `"type"` 设置为 `"6"`。
  * **H8.2**：信令内携带被撤回消息的 `id` / `MSG_ID`。
  * **H8.3**：接收方收到后回送 `<X_SEND_MSG_ACK>`，并将本地对应气泡替换为撤回提示。
* **用户配合操作步骤**：
  1. 宿主机启动 Wireshark 捕获。
  2. 宿主机向 Sandbox 发送一条文本消息 `RECALL_TEST_12345`。
  3. 待 Sandbox 收到显示后，宿主机立即在消息气泡上右键，点击“撤回”。
  4. 观察 Sandbox 窗口中的气泡是否变为“对方撤回了一条消息”。
  5. 停止抓包，保存为 `captures/08-message-recall.pcapng`。
